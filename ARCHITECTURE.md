# Project Architecture

This document provides a high-level overview of the wedding website's architecture. The project is a full-stack application built with Next.js, leveraging its capabilities for both client-side rendering and server-side Route Handlers.

## Core Components

The application is composed of three main parts:

1.  **Frontend:** A React-based user interface built with Next.js App Router.
2.  **Backend:** Serverless Route Handlers built with Next.js App Router.
3.  **Database:** A PostgreSQL database managed with Prisma ORM.

## Deployment Architecture & Single-Site Default

The default supported architecture is **one deployment = one wedding site**:
- **Single Canonical Config**: Every deployment loads a single canonical configuration (`id: "global"`).
- **Simplified Setup**: No wildcard DNS, tenant concepts, or subdomain routing are required for standard setups.
- **Provider-Neutral Host Filtering**: Strict host and `X-Forwarded-Host` validation prevents host header injection and HTTP host spoofing without binding site data to incoming Host headers.
- **Optional Multi-Profile Subdomain Routing**: Subdomain-based `AppConfig` profile routing (`X-Forwarded-Host` checked before `Host` in `src/lib/config.ts`) can be enabled via `MULTISITE_ENABLED=true`. `MULTISITE_ENABLED` switches `AppConfig` branding/profile rows only; `prisma/schema.prisma` shares the other 15 tables across subdomains without tenant row isolation.

## Environment Specifications

For detailed runtime requirements, host configuration, environment variable specifications, and lifecycle expectations, see the authoritative [Application Runtime Contract](./docs/runtime-contract.md).

### 1. Frontend

The frontend is built using [Next.js](https://nextjs.org/) and [React](https://react.dev/). It is responsible for rendering the user interface that guests and administrators interact with.

-   **Location:** `src/app/`
-   **Key Technologies:**
    -   **React:** For building UI components.
    -   **Next.js:** For App Router, server-side rendering, and client-side navigation.
    -   **Tailwind CSS:** For styling.
    -   **Framer Motion:** For animations.
    -   **React Query:** For managing server state, caching, and data fetching.
-   **Structure:**
    -   **App Router (`src/app/`):** Uses the Next.js App Router where directories define the routes and `page.tsx` renders the UI.
    -   **Components (`src/components/`):** Reusable UI elements are located here.
    -   **Admin UI:** A separate set of pages and components under `src/app/admin/` provides an interface for managing the website.

### 2. Backend (API)

The backend is a set of serverless functions implemented as Next.js Route Handlers. These routes handle business logic, data validation, and communication with the database.

- **Location:** `src/app/api/`
- **Key Technologies:**
  - **Next.js Route Handlers:** For creating serverless API endpoints.
  - **Prisma:** As the ORM for database access.
- **Route Groups & Access Tiers:** Most API route handlers under `src/app/api/**/route.{ts,tsx}` wrap execution with `withApiMiddleware` ([src/utils/withApiMiddleware.ts](src/utils/withApiMiddleware.ts)), while specialized binary, probe, and webhook endpoints stream responses directly (exact handler and wrapper totals are synchronized automatically in the inventory below). ### 3. Database

The database stores all application data using PostgreSQL managed via Prisma ORM.

- **Location:** The schema is defined in [prisma/schema.prisma](https://github.com/fderuiter/wedding_website/blob/HEAD/prisma/schema.prisma).
- **Key Technologies:**
  - **PostgreSQL:** Relational database implementing the project's standard database contract (compatible with local PostgreSQL, Neon, Supabase, Railway, AWS RDS, GCP Cloud SQL, etc. as labeled host examples).
  - **Prisma:** The ORM used to define the schema and interact with the database in a type-safe way.
- **Data Models:**
  - **`AppConfig`:** Stores global site settings, partner details, wedding date and venue parameters, visual theme tokens, feature toggles, and email/SMS broadcast provider credentials.
  - **`Media`:** Stores uploaded media metadata (URLs, alt text, decorative/sample flags) referenced by wedding party members, attractions, and registry items.
  - **`WeddingPartyMember`:** Represents members of the wedding party with name, role, bio, side (`BRIDE`, `GROOM`, `JOINT`), display order, and optional media relationship.
  - **`Attraction`:** Represents local attraction and accommodation recommendations, including categories, map coordinates, booking URLs, promo codes, and shuttle information.
  - **`RegistryItem`:** Represents gift registry items with item type, price, display order, quantity, group gift / most wanted flags, purchase status, and total contributed amount.
  - **`Contributor`:** Stores guest financial contributions towards registry items, including contributor contact info, contribution amounts, custom messages, and thank-you note status.
  - **`InvitationCode`:** Stores unique guest invitation passes, guest names, mailing addresses, dietary notes, plus-one allocations, party tags, assigned table and inline seat references (`tableId`, `seatNumber`, `plusOneSeatNumbers`), and projected aggregate RSVP state (`used`, `usedAt`, `plusOneFirstName`, `plusOneLastName`, `dietaryNotes`, and JSON `extraFields`).
  - **`SeatingTable`:** Stores reception seating tables with table name, shape, seat capacity, and floor plan coordinate attributes (`x`, `y`, `width`, `height`, `rotation`).
  - **`ContentNode`:** Provides dynamic CMS content storage for site copy, FAQ entries, announcements, and key-value JSON attributes tagged by domain (including legacy or lightweight `Schedule` and `Logistics` entries that coexist as read-only schedule fallbacks when no `SubEvent` rows match).
  - **`SnapshotVersion`:** Stores audit logs and JSON entity snapshot history for change tracking and point-in-time state restoration.
  - **`SubEvent`:** Represents individual wedding schedule items (e.g., rehearsal dinner, ceremony, reception) in [prisma/schema.prisma](prisma/schema.prisma#L300-L317) with start/end times, venue details, privacy settings (`isPrivate`), and structured JSONB configuration columns (`mealOptions` and `customQuestions`).
  - **`SubEventAccess`:** Junction table defining explicit access permissions for private sub-events mapped to guest invitation codes.
  - **`SubEventRsvp`:** Canonical per-event RSVP table in [prisma/schema.prisma](prisma/schema.prisma#L330-L346) storing attendance `status`, `plusOneCount`, `dietaryNotes`, and structured JSONB response columns (`mealSelections`, `customAnswers`, and `plusOneNames`).
  - **`BroadcastMessage`:** Stores outbound email and SMS communication broadcasts, tracking target filters, delivery status, send timestamps, and dispatch counts.
  - **`BroadcastRecipient`:** Stores individual delivery logs for broadcast messages, recording destination addresses, delivery status, and error details.
- **Canonical `SubEventRsvp` Projection & `ContentNode` Coexistence:**
  - **Canonical `SubEventRsvp` -> `InvitationCode` Synchronization:** Guest submissions (`POST /api/rsvp`) and administrative RSVP overrides in `SubEventService` ([src/features/sub-events/service.ts](src/features/sub-events/service.ts#L604-L1162)) transactionally project aggregate RSVP state from `SubEventRsvp` onto `InvitationCode` (`used`, `usedAt`, `plusOneFirstName`, `plusOneLastName`, `dietaryNotes`, and `extraFields` keys `attendanceStatus`, `plusOneCount`, `plusOneNames`, `dietaryTags`, `mealSelections`, `mealSummary`, `customAnswers`, `customAnswersSummary`, and `eventRsvps`). Downstream seating and roster helpers—specifically `getGuestAttendanceStatus`, `isGuestEligibleForSeating`, and `getDietaryBadges` in [src/features/seating/utils/seatingHelpers.ts](src/features/seating/utils/seatingHelpers.ts#L134-L216)—consume those projected `InvitationCode` fields. `SubEventRsvp` remains authoritative for attendance, meal, and custom-question responses (batch `InvitationCode` edits strip reserved RSVP projection keys rather than back-populating `SubEventRsvp` attendance), while `InvitationCodeAdminService.update` ([src/features/registry/invitation-code.admin.service.ts](src/features/registry/invitation-code.admin.service.ts#L177-L502)) synchronizes updated guest/plus-one names onto attending `SubEventRsvp` records and recomputes projected `InvitationCode.extraFields` summaries.
  - **Read-Only `ContentNode` Schedule Fallbacks:** When a requested schedule item has no `SubEvent` record, `SubEventService` ([src/features/sub-events/service.ts](src/features/sub-events/service.ts#L375-L408)) falls back to `Schedule` or `Logistics` `ContentNode` records with `isReadOnly: true` (enforcing `isPrivateContentNode` access checks and rejecting RSVP submissions against read-only fallback nodes with HTTP `400`). On the homepage, `HomePageClient` ([src/components/home/HomePageClient.tsx](src/components/home/HomePageClient.tsx#L257-L300)) renders `InteractiveTimeline` whenever structured `Schedule` or `startTime` entries exist in `contentNodes` and falls back to `Logistics` ceremony/reception summary cards (`ceremonyTitle`, `receptionTitle`) otherwise.

The use of Prisma allows for easy schema management through migrations and provides a type-safe client for querying the database from the backend API. The project uses PostgreSQL as the sole active database layer for both local development and production.

### 4. Core Framework Infrastructure

To establish consistent data access, transaction management, state auditing, and session security across all application features, the codebase utilizes a centralized core framework layer located in `src/core/`.

#### Infrastructure Data Access Layer (`src/core/infrastructure/`)

- **`BaseRepository` ([src/core/infrastructure/repository.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/infrastructure/repository.ts)):** The foundation for database interactions. It encapsulates standard Prisma CRUD queries (`findMany`, `findUnique`, `create`, `update`, `delete`), supports transactional execution via `transaction()`, and allows client context swapping with `withClient()`. Deletion operations automatically call `createAuditSnapshot` to record deletion audit logs.
- **`BaseService` ([src/core/infrastructure/service.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/infrastructure/service.ts)):** The foundation for business logic services. It wraps `BaseRepository` instances, provides default query argument merging for sorting and relations, and enforces transactional mutation lifecycles. It includes extensibility hooks (`validate`, `preSave`) and manages point-in-time audit snapshot creation (`createSnapshot`) whenever records are created or updated. It also provides a built-in utility for record reordering (`reorder`).

#### Authentication Modules (`src/core/auth/`)

- **Shared Token & Cookie Primitives ([src/core/auth/tokenCookieHelpers.ts](src/core/auth/tokenCookieHelpers.ts)):** Centralizes compact token signing (`signCompactToken` producing `base64url(payload).base64url(signature)` via HMAC-SHA256), constant-time signature verification (`verifyCompactToken` using `timingSafeEqualJS`), and request cookie extraction (`readRequestCookie` reading from `NextRequest.cookies`, raw `cookie` headers, or Next.js Server Component `cookies()`).
- **Server Admin Authentication ([src/core/auth/auth.server.ts](src/core/auth/auth.server.ts)):** Handles server-side administrative session management using `tokenCookieHelpers.ts` and `ADMIN_PASSWORD` as the HMAC signing secret. It provides `signAdminToken`, `verifyAdminToken`, and `isAdminRequest` against the `admin_auth` `HttpOnly` cookie, plus `setAdminAuthCookie` / `getAdminCookieOptions` (`httpOnly`, `sameSite: 'lax'`, `secure` in production, 8-hour default `maxAge`).
- **Client Admin Authentication ([src/core/auth/auth.client.ts](src/core/auth/auth.client.ts)):** Provides client-side session verification via `checkAdminClient()`, which queries the `Public` `GET /api/admin/me` endpoint (returning `{ success: true, isAdmin: false }` when unauthenticated) without requiring a guest cookie or exposing internal token secrets, while `POST /api/admin/logout` clears stale `admin_auth` cookies cleanly.
- **Server Guest Authentication ([src/core/auth/guest.server.ts](src/core/auth/guest.server.ts)):** Manages shared-passcode guest sessions via `tokenCookieHelpers.ts`. It signs and verifies `guest_auth` tokens (`signGuestToken`, `isGuestRequest`) exclusively with `GUEST_SESSION_SECRET` (requiring a distinct secret of at least 32 characters in production and throwing an error whenever `secret === passcode`, i.e., `GUEST_SESSION_SECRET === GUEST_PASSCODE`).
- **Stateless Edge Guest Invite Token ([src/core/auth/guestInviteToken.ts](src/core/auth/guestInviteToken.ts#L46-L122)):** Implements Tier 1 Edge-safe token signing and stateless verification (`signGuestInviteSessionToken`, `verifyGuestInviteSessionToken`, `getSignedGuestInviteSession`) for the 7-day `guest_invite_session` cookie using `GUEST_SESSION_SECRET` (>= 32 characters in production, rejecting `secret === passcode`) with zero Prisma or Node-only dependencies so [src/middleware.ts](src/middleware.ts) runs cleanly in the Edge runtime.
- **Database-Backed Guest Invitation Session & Revocation ([src/core/auth/guestInviteSession.ts](src/core/auth/guestInviteSession.ts#L52-L239)):** Implements Tier 2 Node/Server session validation and immediate revocation (`getGuestInviteSession`, `enforceActiveGuestPageSession`, backed by per-request hydration in [src/lib/requestContext.ts](src/lib/requestContext.ts)). After verifying the signed cookie via `getSignedGuestInviteSession`, it queries `prisma.invitationCode` to confirm the invitation code still exists and has `isSample: false`—immediately invalidating deleted, rotated, or purged sample sessions. On guest-gated SSR pages, `RootLayout` ([src/app/layout.tsx](src/app/layout.tsx#L116-L118)) calls `enforceActiveGuestPageSession()`, issuing a `303 See Other` redirect to `/guest/login` when a `guest_invite_session` is revoked and neither `admin_auth` nor `guest_auth` is valid. On non-excluded API routes (`isInviteRevocationExcludedApiPath` in [src/utils/withApiMiddleware.ts](src/utils/withApiMiddleware.ts#L39-L175)), `withApiMiddleware` calls `getGuestInviteSession(req)` and responds with HTTP `401` while clearing `guest_invite_session` (`maxAge: 0`) when no fallback `admin_auth` or `guest_auth` cookie exists.
- **Guest Login vs. Read-Only Lookup Endpoints ([src/app/api/guest/login/route.ts](src/app/api/guest/login/route.ts), [src/app/api/guest/lookup/route.ts](src/app/api/guest/lookup/route.ts)):** `POST /api/guest/login` authenticates credentials and mints 7-day `HttpOnly` cookies—issuing `guest_auth` when matching the shared `GUEST_PASSCODE` (via constant-time SHA-256 comparison) or `guest_invite_session` when matching a non-sample (`isSample: false`) `InvitationCode`. By contrast, `POST /api/guest/lookup` (throttled to 5 failed attempts per 15 minutes in `withApiMiddleware`) performs a read-only search across non-sample `InvitationCode` records by name, plus-one name, or email and returns only `{ guestName }` without minting cookies or exposing invitation codes.

### 5. Feature Organization

To maintain modularity and prevent logic smear, the codebase adopts a strict layered feature architecture. All domain-specific logic is encapsulated in isolated feature directories under `src/features/`.

-   **Location:** `src/features/`
-   **Structure:** Each feature scaffolded by [scripts/scaffold-feature.mjs](scripts/scaffold-feature.mjs#L30) contains:

### 6. Architectural Boundaries & Shared Components Guidelines

To prevent code duplication and maintain clear ownership boundaries while preserving file-path stability for downstream template forks, the codebase balances feature encapsulation with documented shared-folder exceptions.

#### Folder Boundaries
* **Generic & Cross-Cutting Shared Directories (`src/components/`, `src/components/ui/`, `src/utils/`, `src/lib/`):**
  * New reusable UI primitives (e.g., `Button`, `Dialog` in `src/components/ui/`) and stateless helpers (e.g., `cn` in `src/utils/cn.ts`) belong in these shared directories and should stay domain-agnostic.
  * **Documented Shared-Folder Exceptions (Preserved for Downstream Fork Stability):** Core runtime singletons and cross-cutting services intentionally reside at stable paths under `src/lib/`, `src/utils/`, and `src/components/` so downstream adopters merge upgrades cleanly without path churn:
    * `src/lib/`: Database connection singletons (`prisma.ts`, `postgresPool.ts`), global `AppConfig` resolution (`config.ts`), snapshot audit logging (`audit.ts`), theme/preset engines (`theme/presets.ts`, `theme/stylesheet.ts`), module registry (`modules.ts`), and sample data seeding (`sampleData/generator.ts`).
    * `src/utils/`: Cross-route API middleware (`withApiMiddleware.ts`), backup/invitation/RSVP validation helpers (`backupValidation.ts`, `invitationValidation.ts`, `rsvpDeadline.ts`), and calendar/pagination utilities.
    * `src/components/`: Root layout providers (`ThemeProvider.tsx`, `RootLayoutClient.tsx`), multi-feature page orchestrators (`home/HomePageClient.tsx`), and onboarding/admin shells (`setup/SetupWizard.tsx`).
* **Feature Directories (`src/features/<feature-name>/`):**
  * Feature directories contain UI components, hooks, internal `lib/` helpers, schema definitions, repositories, and services scoped to a single domain (e.g., `weather`, `registry`, `seating`, `sub-events`, `broadcast`).
  * Feature internals must not be imported directly across module boundaries; external callers import exclusively through the feature's public barrel (`@/features/<feature-name>`, backed by `src/features/<feature-name>/index.ts`) as enforced by `eslint.config.mjs`.

#### Structural Rules for Shared UI Primitives
Shared UI primitives added to `src/components/ui/` must adhere to the following design and quality patterns:

1. **React Ref Forwarding (DOM-Wrapping Primitives):**
   * Interactive and layout primitives that wrap a single underlying DOM element (such as `Button`, `Input`, `Select`, `Textarea`, `Checkbox`, `Dialog`, `Table`, `Icon`, `Skeleton`, and `Layout` primitives) must forward `ref` to their root DOM node using React 19 `ref` props (`React.ComponentPropsWithRef<'...'>`, or `React.forwardRef`).
   * Stateful, context, portal/provider, or error-boundary components in `src/components/ui/` that do not represent a single ref-target DOM element (`ErrorBoundary`, `GlobalRadialGlow`, `RouteErrorFallback`, `ThemeSelector`, and `ToastProvider`) are exempt from DOM `ref` forwarding.
   * *Example:*
     ```tsx
     import React from 'react';
     import { cn } from '@/utils/cn';

     export interface InputProps extends React.ComponentPropsWithRef<'input'> {}

     export function Input({ className, type, ref, ...props }: InputProps) {
       return (
         <input
           type={type}
           className={cn('border rounded px-3 py-2', className)}
           ref={ref}
           {...props}
         />
       );
     }
     ```

2. **Style Composition / Class Merging:**
   * Primitives must be highly configurable from the outside. Default Tailwind styles must be composed with custom styles passed via the `className` prop.
   * Class composition uses the lightweight `cn(...)` helper in [src/utils/cn.ts](src/utils/cn.ts) (`classes.filter(Boolean).join(' ')`), which filters falsy values and joins truthy class strings with spaces **without** performing Tailwind utility conflict resolution (`tailwind-merge` is not installed). Avoid passing conflicting Tailwind utilities in base and override class strings.
   * *Example:*
     ```tsx
     import { cn } from '@/utils/cn';
     // Usage inside a component:
     className={cn('base-classes-here', className)}
     ```

3. **Unit Tests:**
   * Every new shared UI primitive must have a matching unit test file inside the respective `__tests__` directory (e.g., `src/components/ui/__tests__/<Component>.test.tsx`).
   * Unit tests must verify proper rendering, prop-based configuration, custom ref forwarding, and interactive behavior (e.g., fire events).

### Theme Token Precedence, WCAG Contrast Calibration, & Zero-FOUC Hydration

- **Sparse `themeTokens` Diffing (`stripPresetDefaultTokens`, [src/lib/theme/presets.ts](src/lib/theme/presets.ts#L1925-L1980)):** `AppConfig.themeTokens` stores only sparse custom `--*` CSS token overrides rather than full preset dumps. `stripPresetDefaultTokens` strips entries matching the active preset's light defaults, the previous preset's defaults, or legacy hydrated payloads (>= 25 matching preset keys) so switching `themePreset` never carries stale preset defaults forward. Effective token precedence resolves deterministically as `APP_DEFAULTS` -> `THEME_PRESETS[themePreset]` -> sparse database `themeTokens` -> sparse `SITE_THEME_TOKENS`.
- **WCAG Contrast Calibration & Dark Surface Tiers ([src/lib/theme/stylesheet.ts](src/lib/theme/stylesheet.ts#L171-L729)):** `optimizeContrast` binary-searches HSL lightness across 7 iterations (memoized in the bounded 1,000-entry `contrastCache`) to guarantee >= `4.5:1` text contrast and >= `3.0:1` UI/focus-ring contrast against target backgrounds. `generateDynamicStyles` and `generateThemeStylesheet` emit calibrated `:root` light-mode variables alongside `.dark` / `[data-theme="dark"]` dark-mode palettes across three surface tiers: base dark surfaces (`800` / `900` / `950` / `#000000`), elevated `700` cards, and interactive `600` controls.
- **Zero-FOUC `<head>` Script & `ThemeProvider` Synchronization ([src/app/layout.tsx](src/app/layout.tsx#L147-L174), [src/components/ThemeProvider.tsx](src/components/ThemeProvider.tsx)):** `RootLayout` injects the server-compiled `<style id="dynamic-theme-style">` tag and a blocking inline `themeScript` in `<head>` that reads `localStorage.getItem('theme_mode')`, falls back to the `theme_mode` cookie or `prefers-color-scheme: dark`, and applies `.dark` / `.light` on `<html>` prior to first paint. On hydration, `ThemeProvider` (`hasServerStylesheet`) adopts the server stylesheet without FOUC and keeps `localStorage` and the `theme_mode` cookie synchronized when guests toggle modes.

#### Deterministic Precedence Hierarchy
```
Deployment Config (Environment Overrides / Secrets)
       ↓ (overrides)
Site Configuration (Database AppConfig)
       ↓ (falls back to)
Application Defaults (Generic Technical Fallbacks)
```

Every configurable value has one authoritative home. Ordinary site customization requires zero source code edits.
