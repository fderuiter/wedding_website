# Project Architecture

This document provides a high-level overview of the wedding website's architecture. The project is a full-stack application built with Next.js, leveraging its capabilities for both client-side rendering and server-side Route Handlers.

## Core Components

The application is composed of three main parts:

1.  **Frontend:** A React-based user interface built with Next.js App Router.
2.  **Backend:** Serverless Route Handlers built with Next.js App Router.
3.  **Database:** A PostgreSQL database managed with Prisma ORM.

## Deployment Architecture & Single-Site Default

The default supported architecture is **one deployment = one wedding site**:
- **Single Canonical Config**: Every deployment loads a single canonical configuration (`id: "global"`).
- **Simplified Setup**: No wildcard DNS, tenant concepts, or subdomain routing are required for standard setups.
- **Provider-Neutral Host Filtering**: Strict host and `X-Forwarded-Host` validation prevents host header injection and HTTP host spoofing without binding site data to incoming Host headers.
- **Optional Multi-Site Module**: Multi-profile management and subdomain-based routing can be explicitly enabled via `MULTISITE_ENABLED=true` for advanced setups.

## Environment Specifications

For detailed runtime requirements, host configuration, environment variable specifications, and lifecycle expectations, see the authoritative [Application Runtime Contract](./docs/runtime-contract.md).

### 2. Backend (API)

The backend is a set of serverless functions implemented as Next.js Route Handlers. These routes handle business logic, data validation, and communication with the database.

- **Location:** `src/app/api/`
- **Key Technologies:**
  - **Next.js Route Handlers:** For creating serverless API endpoints.
  - **Prisma:** As the ORM for database access.
- **Route Groups:**
  - **Admin Routes (`src/app/api/admin/`):** Handle administrator authentication (`login`, `logout`, `me`, `setup`), feature flags, entity CRUD operations, email/SMS broadcasts (`send`, `history`, `preview`, `retry`, `schedule`, `test-connection`), invitation codes (`batch`, `export`, `validate`), seating assignments (`assign`, `export`), sub-events access management, thank-you notes (`batch`, `export`, `export-labels`), media uploads, version restoration, sample data seeding, and database maintenance (`export`, `import`).
  - **Cron Routes (`src/app/api/cron/`):** Provide scheduled serverless tasks, including `src/app/api/cron/broadcasts/` for executing pending email and SMS message delivery queues.
  - **Guest Routes (`src/app/api/guest/`):** Provide guest authentication (`login`), guest photo upload endpoints (`photos/upload`), and mailing address collection (`address` and `address/public`).
  - **Health Check Route (`src/app/api/health/`):** Server liveness probe returning HTTP 200 health status for infrastructure health monitoring and container orchestration.
  - **Media Routes (`src/app/api/media/`):** Resolve uploaded media assets by ID (`[id]`) and support bulk media file archive exports (`export`).
  - **Open Graph Route (`src/app/api/og/`):** Generate dynamic Open Graph social preview cards on the fly based on configuration branding settings.
  - **Photos Route (`src/app/api/photos/`):** Handle public guest photo gallery uploads (`upload`).
  - **Readiness Probe Route (`src/app/api/ready/`):** Server readiness probe checking database connectivity and system readiness before taking traffic.
  - **Registry Routes (`src/app/api/registry/`):** Manage gift registry items (`items`), guest contributions (`contribute`), invitation code validation (`validate-code`), guest contribution session management (`session`), and external product URL metadata scraping (`scrape`).
  - **RSVP Routes (`src/app/api/rsvp/`):** Handle guest RSVP submissions and invitation code lookups.
  - **Schedule Routes (`src/app/api/schedule/`):** Serve wedding event timeline items and sub-events filtered by guest access permissions.
  - **Weather Forecast Route (`src/app/api/weather/`):** Fetch live weather forecasts and conditions for the venue location.

### 3. Database

The database stores all application data using PostgreSQL managed via Prisma ORM.

- **Location:** The schema is defined in [prisma/schema.prisma](https://github.com/fderuiter/wedding_website/blob/HEAD/prisma/schema.prisma).
- **Key Technologies:**
  - **PostgreSQL:** Relational database implementing the project's standard database contract (compatible with local PostgreSQL, Neon, Supabase, Railway, AWS RDS, GCP Cloud SQL, etc. as labeled host examples).
  - **Prisma:** The ORM used to define the schema and interact with the database in a type-safe way.
- **Data Models:**
  - **`AppConfig`:** Stores global site settings, partner details, wedding date and venue parameters, visual theme tokens, feature toggles, and email/SMS broadcast provider credentials.
  - **`Media`:** Stores uploaded media metadata (URLs, alt text, decorative/sample flags) referenced by wedding party members, attractions, and registry items.
  - **`WeddingPartyMember`:** Represents members of the wedding party with name, role, bio, side (`BRIDE`, `GROOM`, `JOINT`), display order, and optional media relationship.
  - **`Attraction`:** Represents local attraction and accommodation recommendations, including categories, map coordinates, booking URLs, promo codes, and shuttle information.
  - **`RegistryItem`:** Represents gift registry items with item type, price, display order, quantity, group gift / most wanted flags, purchase status, and total contributed amount.
  - **`Contributor`:** Stores guest financial contributions towards registry items, including contributor contact info, contribution amounts, custom messages, and thank-you note status.
  - **`InvitationCode`:** Stores unique guest invitation passes, guest names, mailing addresses, dietary notes, plus-one allocations, party tags, assigned table references, and RSVP state.
  - **`SeatingTable`:** Stores reception seating tables with table name, shape, seat capacity, and floor plan coordinate attributes (`x`, `y`, `width`, `height`, `rotation`).
  - **`ContentNode`:** Provides dynamic CMS content storage for site copy, FAQ entries, announcements, and key-value JSON attributes tagged by domain.
  - **`SnapshotVersion`:** Stores audit logs and JSON entity snapshot history for change tracking and point-in-time state restoration.
  - **`SubEvent`:** Represents individual wedding schedule items (e.g., rehearsal dinner, ceremony, reception) with start/end times, venue details, and privacy settings.
  - **`SubEventAccess`:** Junction table defining explicit access permissions for private sub-events mapped to guest invitation codes.
  - **`SubEventRsvp`:** Stores guest RSVP responses for specific sub-events, including attendance status, plus-one counts, and dietary notes.
  - **`BroadcastMessage`:** Stores outbound email and SMS communication broadcasts, tracking target filters, delivery status, send timestamps, and dispatch counts.
  - **`BroadcastRecipient`:** Stores individual delivery logs for broadcast messages, recording destination addresses, delivery status, and error details.

The use of Prisma allows for easy schema management through migrations and provides a type-safe client for querying the database from the backend API. The project uses PostgreSQL as the sole active database layer for both local development and production.

### 4. Core Framework Infrastructure

To establish consistent data access, transaction management, state auditing, and session security across all application features, the codebase utilizes a centralized core framework layer located in `src/core/`.

#### Infrastructure Data Access Layer (`src/core/infrastructure/`)

- **`BaseRepository` ([src/core/infrastructure/repository.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/infrastructure/repository.ts)):** The foundation for database interactions. It encapsulates standard Prisma CRUD queries (`findMany`, `findUnique`, `create`, `update`, `delete`), supports transactional execution via `transaction()`, and allows client context swapping with `withClient()`. Deletion operations automatically call `createAuditSnapshot` to record deletion audit logs.
- **`BaseService` ([src/core/infrastructure/service.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/infrastructure/service.ts)):** The foundation for business logic services. It wraps `BaseRepository` instances, provides default query argument merging for sorting and relations, and enforces transactional mutation lifecycles. It includes extensibility hooks (`validate`, `preSave`) and manages point-in-time audit snapshot creation (`createSnapshot`) whenever records are created or updated. It also provides built-in utilities for record reordering (`reorder`) and visibility toggling (`toggleVisibility`).

#### Authentication Modules (`src/core/auth/`)

- **Server Admin Authentication ([src/core/auth/auth.server.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/auth/auth.server.ts)):** Handles server-side administrative session management. It provides `signAdminToken` to issue HMAC-SHA256 signed session tokens, `verifyAdminToken` and `isAdminRequest` to authenticate incoming API requests and Server Components against the `admin_auth` HttpOnly cookie, and `setAdminAuthCookie` / `getAdminCookieOptions` to configure cookie security flags (`httpOnly`, `sameSite`, `secure`, `maxAge`).
- **Client Admin Authentication ([src/core/auth/auth.client.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/auth/auth.client.ts)):** Provides client-side session verification via `checkAdminClient()`, which queries the `/api/admin/me` endpoint to confirm administrator authentication status securely without exposing internal token secrets.
- **Server Guest Authentication ([src/core/auth/guest.server.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/auth/guest.server.ts)):** Manages general guest passcode authentication. It signs guest tokens using `GUEST_PASSCODE` secret key (`signGuestToken`) and validates incoming guest sessions (`isGuestRequest`) via the `guest_auth` cookie.
- **Guest Invitation Session ([src/core/auth/guestInviteSession.ts](https://github.com/fderuiter/wedding_website/blob/HEAD/src/core/auth/guestInviteSession.ts)):** Manages personalized guest invitation sessions. It issues 7-day compact invitation tokens (`signGuestInviteSessionToken`) carrying guest invitation codes and names, and retrieves verified sessions (`getGuestInviteSession`) from the `guest_invite_session` cookie to control personalized RSVP and sub-event access.

### 5. Feature Organization

To maintain modularity and prevent logic smear, the codebase adopts a strict layered feature architecture. All domain-specific logic is encapsulated in isolated feature directories under `src/features/`.

-   **Location:** `src/features/`
-   **Structure:** Each feature contains:
    -   `api/`: Route handlers and server-side logic (e.g., proxying).
    -   `components/`: UI components specific to the feature.
    -   `hooks/`: Custom React hooks.
    -   `repository.ts`: Data access layer for Prisma queries.
    -   `service.ts`: Business logic layer.
    -   `schemas.ts`: Validation schemas (Zod).
    -   `types.ts`: TypeScript interfaces.
    -   `index.ts`: The public interface. To prevent cross-domain internal leakage, other modules must solely import from this file.

New features should be scaffolded using the included CLI utility (`npm run scaffold <feature-name>`) to ensure correct structural boundaries and naming conventions.

### 6. Architectural Boundaries & Shared Components Guidelines

To prevent code duplication, maintain a highly maintainable and clean project structure, developers must respect the strict boundaries between generic (shared) directories and feature-specific directories.

#### Folder Boundaries
* **Generic Directories (`src/components/`, `src/components/ui/`, `src/utils/`, `src/lib/`):**
  * These directories must house ONLY domain-agnostic, reusable components, hooks, or helpers.
  * No feature-specific terminology, business rules, or Prisma/database imports should exist in these files.
  * For example, a generic `Button` or `Dialog` goes to `src/components/ui/`. A generic `cn` style merger goes to `src/utils/`.
* **Feature Directories (`src/features/<feature-name>/`):**
  * Feature directories contain all UI components, hooks, schema definitions, and business logic that belong strictly to that feature domain (e.g., weather, registry).

## Upstream Compatibility & Downstream Upgrade Architecture

To treat upstream compatibility as a product feature for downstream template adopters, the architecture enforces strict separation between application code, personal content, and deployment configuration:

- **Personal Content Isolation**: Couple details, venue information, story text, wedding party members, registry items, and photos reside in PostgreSQL database models (`AppConfig`, `Media`, `RegistryItem`, `WeddingPartyMember`, `ContentNode`). Avoid hardcoding personal details into React page components (`src/app/` or `src/features/`).
- **Deployment Isolation**: Provider configurations and secret credentials are injected via environment variables (`DATABASE_URL`, `ADMIN_PASSWORD`, etc.) using a provider-neutral container setup.
- **Database Schema Evolution**: Schema updates are managed via immutable Prisma migration scripts (`prisma/migrations/`). Downstream adopters apply updates via `npm run migrate:deploy` (`prisma migrate deploy`), preserving custom database records.
- **Configuration Schema Versioning**: `AppConfig` schema changes utilize Zod default value fallbacks (`src/features/content/schemas.ts`) to ensure non-destructive upgrades for existing database instances.

## System Configuration

### Configuration Architecture & Precedence Hierarchy
The application follows a strict 4-layer configuration architecture with deterministic precedence:

1. **Deployment Configuration (Layer 1):** Environment variables & secrets (e.g., `DATABASE_URL`, `ADMIN_PASSWORD`, `ALLOWED_HOSTS`, `GUEST_PASSCODE`, `S3_*`, and `SITE_*` environment variable overrides such as `SITE_BRIDE_NAME`, `SITE_GROOM_NAME`, `SITE_WEDDING_DATE`, `SITE_VENUE_NAME`, `SITE_TIMEZONE`, `SITE_COLOR_PRIMARY`).
2. **Site Configuration (Layer 2):** Database-persisted site settings (`AppConfig` table: partner names, wedding date, venue details, colors, timezone, feature toggles, SEO metadata).
3. **Site Content (Layer 3):** Editable content nodes (`ContentNode` table: stories, wedding party members, FAQs, travel advice, local attractions, registry items).
4. **Application Defaults (Layer 4):** Domain-agnostic technical defaults (`APP_DEFAULTS` in `src/lib/config.ts`) with generic placeholder fallbacks and zero personal wedding content.

#### Deterministic Precedence Hierarchy
```
Deployment Config (Environment Overrides / Secrets)
       ↓ (overrides)
Site Configuration (Database AppConfig)
       ↓ (falls back to)
Application Defaults (Generic Technical Fallbacks)
```

Every configurable value has one authoritative home. Ordinary site customization requires zero source code edits. At runtime boundaries (especially in production), configuration payloads are validated against Zod schemas (`AppConfigSchema`), ensuring immediate, clear failure if misconfigured. Secret credentials and sensitive keys are stripped from public DTOs and database export backups via `toPublicAppConfig`. Import and export formats include versioning metadata (`schemaVersion: "1.0"`) to guarantee upgrade safety.
